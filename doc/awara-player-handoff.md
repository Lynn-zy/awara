### B. 横滑与共享进度预览已通过用户实机验收

改造前的问题和源码证据：

- `Player.kt` 的 `detectHorizontalDragGestures` 直接把每个事件的 dp 转为 Long 后乘以 `300`，导致灵敏度过高、事件频率依赖和小位移不稳定。
- 横滑期间只更新中央时间文字，不驱动底部进度条目标位置，也没有视频画面预览。
- 当前没有明确的横向/纵向方向锁和顶部系统手势区域避让，用户反馈下拉通知栏可能误触发 seek。
- buffering 时底部 Slider 被替换成不确定的 `LinearProgressIndicator`，短暂 seek 等待会变成明显转圈。

本阶段结果：

- `SeekPreviewState` 统一横滑与 Slider 的目标位置、时间与正负偏移；真实进度只轮询一份，提交后短暂保留目标，播放器位置到达或 1.5 秒超时后清除，避免旧位置回弹。
- 横向位移超过系统 touch slop，且至少为纵向的 1.5 倍才锁定 seek；竖向或方向不明确时拒绝该序列。使用起始位置和累计浮点位移计算，整宽时间窗为 `min(60 秒, 总时长 / 2)`，目标限制在有效时长内。
- 以窗口坐标结合实际系统 inset 和至少 24dp 边缘保护避让系统手势；子控件优先，保留标准单击、双击。多指、取消、失焦、切后台、换媒体及尺寸/全屏变化取消未提交目标。
- 横滑预览立即驱动 Slider，滑动中不反复 seek，正常松手提交一次。Slider 取消和多指序列同步门控，键盘及无障碍进度操作仍走原生 Slider。
- 控制栏在拖动期间保持可见，结束后重新计时；Slider 单独成行，缓冲时不卸载。中心 loading 延迟 350ms，预览中不遮挡时间；这仅改善反馈，不代表实际解码或 seek 延迟已优化。
- 本轮只改播放器控制层、新增共享状态和手势模块及两类测试，不改 Media3 内核、数据库、依赖、版本、高刷配置或精确 seek 策略。

- `SeekThumbnailLoader` 串行处理请求，100ms 合并窗口只保留最新待处理目标；以实际 URI 和秒级目标分桶，LRU 缓存同时限制 4MiB 与 12 帧。取消、切源和关闭立即隐藏预览，代次检查拒绝迟到结果。

- 协程不能强制打断系统同步 native 解码；这里保证取消后的结果失效与最终资源释放，不声称能立即终止底层调用，也未测量实际预览或 seek 耗时。
- 预览位于标题与底部控件之间，先测量时间文字，再用剩余空间等比显示图像；大字号或空间不足时保留时间、隐藏图像。加载与不可用状态有固定图像区域，错误不阻断手势和最终跳转。

- 增加同版本官方 `media3-inspector-frame:1.11.1`，使用独立 `FrameExtractor` 异步提取附近关键帧，等比输出到最多 320×180。其默认策略优先软件解码，但不保证所有格式都能用软件解码或都能出图。
- 在线取帧新建自己的 `CacheDataSource.Factory`，仅读取主工厂的缓存与缓存键，复用相同磁盘分片但不修改主播放器上游配置。连接/读取超时均为 1500ms，预览专属加载策略关闭自动重试。
- 单次目标的网络正文读取预算为 2MiB，跨连接累计，本地缓存读取不计入；回调在读后发生，因此可能多出最后一个读取块，HTTP 头部、TLS 和系统缓冲不在此预算内，不能表述为严格的实际流量配额。超额后在后续连接初始化阶段拒绝继续读取。
- 帧等待预算为 2 秒，取消 Future 后在 `finally` 释放独立提取器；这不是底层网络或解码的实时强制终止保证。请求串行，网络合并间隔 350ms，本地仍为 100ms；新目标取消旧子请求，代次校验拒绝迟到结果，超时不结束整个调度器。
- 在线失败、超时或超额后撤掉图像占位，只保留随滑块移动的时间提示，不中断正常播放或最终跳转。未缓存位置会有额外网络和解码开销，目前没有量化的播放吞吐与流量数据。
- 本地仍使用平台取帧器，HTTP(S) 明确禁止进入该接口；请求守门拒绝无效来源、端口和内嵌 URL 凭据。复用缓存键时已移除原先输出完整签名播放 URL 的日志，键算法不变。

### C. 本地 seek 延迟

- 当前 `PlayerState.seekTo` 只调用 `player.seekTo`，没有重建播放器或换源。
- 精确 seek 可能需要从目标前的关键帧重新解码并丢弃中间帧，即使文件在本地也可能短暂等待。
- 先测量“松手到目标首帧”的时间、目标视频容器/关键帧间隔和是否发生重新加载，再决定是否为拖动预览使用较宽松的关键帧 seek。不要未经验证全局改成不精确跳转。

本轮新增 `LocalSeekLatencyTest.measurePausedAndPlayingLocalExactSeeks`，提供可重复执行的测量入口：

- 复用生产的 `rememberPlayerState` 与 `PlayerBase`，在真实 Surface 上播放本地素材；断言当前仍为 `SeekParameters.EXACT`，不修改两个播放器 Builder。
- 默认使用既有两秒 H.264 合成素材，只验证测量链路。暂停/播放状态各采样 8 次，在当前进度的远侧 25% / 75% 位置间大跨度跳转；小样本中位数、最近秩 P95 和有效样本数以 `AwaraSeekLatency` 标签输出。
- 起点是 `PlayerState.seekTo` 调用，不包含松手事件分发；终点分别为 `VideoFrameMetadataListener` 中首个目标附近帧回调及其计划释放时间，不能把 `READY`、位置不连续或计划释放等同于 SurfaceFlinger 实际上屏。测量的是同一已打开媒体的热 seek，不含首播冷启动。
- 使用 `System.nanoTime()` 同一时钟域计时，按帧率限制目标 PTS 容差，并通过原子引用一次消费结果；旧位置与目标大幅分离，降低旧帧误匹配风险。任意小跨度或特殊时间戳素材不在该基线的保证范围内。
- `releaseTimeNs == C.TIME_UNSET` 单独作为不可用值，不转换为负延迟，也不混入计划释放统计。超时、播放错误或没有目标帧使测试失败，不把这些事件当作快速成功。
- 仪器参数 `seekVideoUri` 可替换为应用已获读取权限的本地 `file://` / `content://` 视频；拒绝网络来源，不请求外网、不输出来源 URI 或标题。至少需要 1.5 秒且带有效视频时间轴的素材；真实高码率、长 GOP 文件需要另行采样。
- 用例只进入测试 APK，不给日常播放器增加日志/监听开销；最终释放帧监听、播放器及临时素材。Debug 仪器环境的数据仅适用于同设备、同素材、同构建配置对照，不能当作 Release 性能承诺。
- 当前没有连接设备或 AVD，已完成编译、测试 APK 打包，未执行该用例，尚无可信的真实耗时或根因结论。
